# Рекомендации для виджета amoCRM + биллинг

> Уроки с проекта «Дубли» — чтобы сразу сделать лучше.
> Разбито по слоям: виджет → бэкенд → оплата → вендорская CRM → жизненный цикл → тестирование.
> В конце — чек-лист перед запуском.

## 1. Виджет (frontend)

- **1.1. Локации = функции.** Показываешь что-то в карточке — в `manifest.locations` должны быть
  `lcard-1`/`ccard-1`/`comcard-1`, а в `script.js` — ветки `render`. Каждая возможность =
  локация + колбэк + i18n. Лишний код/строки без локаций — удалять.
- **1.2. `code` и `secret_key` в манифесте с первого дня** (совпадают с кабинетом разработчика).
  Обязательны для приватной и маркетплейс-интеграции.
- **1.3. Типы полей настроек.** Секреты — тип `pass` (не `text`). Обязательные поля
  (`backend_url`, `security_key`) — `required: true`.
- **1.4. Экранирование (XSS).** Все динамические значения через `escapeHtml` (email, телефон,
  субдомен, имена, суммы). Лучше — Twig-шаблоны + `render_template`.
- **1.5. Обработчики событий — с namespace.** При `init_once: false` виджет пересоздаётся на каждой
  SPA-навигации: `.off('click.mywidget').on('click.mywidget', …)`.
- **1.6. Ошибки — показывать пользователю** (`AMOCRM.notifications.add_alert`), не маскировать
  заглушками; «сырую» причину логировать.
- **1.7. Версионирование.** Виджет сам не обновляется — пересобирать zip и поднимать `version`
  (semver). Бэкенд и виджет катить согласованными версиями.
- **1.8. i18n-паритет.** Ключи из `manifest`/`script.js` существуют во всех локалях из `locale`.
- **1.9. Упаковка.** `manifest.json` в корне архива; исключать `.DS_Store`/`__MACOSX`;
  `installation` строкой `"y"`/`"n"`.

## 2. Бэкенд: конфигурация и секреты

- **2.1. `env_file` с первого дня.** Самая дорогая ошибка «Дублей»: биллинг читал `YOOKASSA_*`/`VENDOR_*`,
  но compose их не пробрасывал → 503. У backend — `env_file: [.env]`, критичное дублировать в
  `environment:`. Новая переменная — сразу и в `.env.example`, и в проброс.
- **2.2. Валидация env на старте (fail-fast).** Схема с понятными ошибками; пустые строки (`VAR=`) → `default()`.
- **2.3. Секреты только в `.env`, никогда в git.** В репозитории — только плейсхолдеры в `.env.example`.
- **2.4. Общий секрет виджет↔бэкенд.** `WEBHOOK_SECURITY_KEY` — заголовком `X-Security-Key`, не в URL.
  Значение в настройках виджета обязано совпадать с `.env`.

## 3. Оплата (ЮKassa / эквайринг РФ)

- **3.1. 54-ФЗ / чек с самого начала.** При онлайн-кассе каждый платёж = объект `receipt`
  (позиции + `vat_code` + контакт), иначе `400 "Receipt is missing or illegal"`. Настраиваемо:
  `YOOKASSA_FISCAL`, `YOOKASSA_VAT_CODE` (УСН = 1 «без НДС»).
- **3.2. Контакт покупателя для чека — обязателен** (email или телефон): поле в форме оплаты,
  бэкенд принимает и валидирует (пустой → понятная ошибка, не 500).
- **3.3. Хостед-оплата и вебхук.** Карточные данные через свой сервер не проводить — только
  hosted-страница ЮKassa (`confirmation_url` → redirect). Вебхук `payment.succeeded`/`canceled`
  не доверять телу — перепроверять по id через API; отвечать `200`. Опц. IP-allowlist на nginx.
- **3.4. Тест без реальных денег.** Тестовый магазин ЮKassa + `test_` ключ. На `live_` тест = реальные деньги.

## 4. Интеграция с вендорской (своей) amoCRM

- **4.1. Долгосрочный токен, а не OAuth-установка вендора.** Внешняя (API) интеграция в вендор-аккаунте
  (Настройки → Интеграции → Создать → «Внешняя интеграция», доступ «Все») + долгосрочный токен в
  `.env` (`VENDOR_AMOCRM_TOKEN`). Не зависит от переустановок виджета.
- **4.2. Проверять сущность кастом-поля.** Засада «Дублей»: поле «ID аккаунта amo» (`1173679`) оказалось
  полем КОМПАНИИ, запись в lead → `400 NotSupportedChoice`. Перед записью сверять
  `GET /api/v4/{leads|contacts|companies}/custom_fields`. Не угадывать по подписи в UI.
- **4.3. Модель данных сделки-счёта.** `account_id` → на компании, телефон/email → на контакте,
  оба линковать к сделке (`POST /api/v4/leads/{id}/link`). Не писать контакты только в примечание.
- **4.4. Дедуп — обязательно.** Искать компанию по account_id/имени, контакт по телефону/email;
  найдено → привязать, нет → создать. Хранить `vendor_company_id`/`vendor_lead_id`.
- **4.5. Субдомен/ID единообразно.** У «Дублей» `.env` хранил `koagency.amocrm.ru`, а БД — `koagency`
  → поиск не совпадал. Нормализовать формат (или числовой `account_id`) + тест.
- **4.6. Этапы — по явным ID, не по названию.** `VENDOR_AMOCRM_STATUS_*` явными ID
  (`GET /api/v4/leads/pipelines/{id}`). Обязательные поля этапа могут блокировать переходы.

## 5. Жизненный цикл: установка → счёт → оплата

- **5.1. Сделка при установке** (`onInstall` → сделка на этапе «установлен»), best-effort.
- **5.2. Бэкфилл** для уже установленных без сделки — идемпотентный скрипт (пропускает с `vendor_lead_id`).
- **5.3. Идемпотентность и «оживление».** Повторная авторизация не плодит сделки; удалена (404) →
  пересоздать; транзиентная 5xx → ретрай, не дубль.
- **5.4. Данные приходят не сразу.** При OAuth телефона ещё нет — поэтапное обогащение (`saveContact`).

## 6. Тестирование и наблюдаемость

- **6.1. Серверные smoke-тесты** (`curl` с `X-Security-Key`): `/health`, `checkout` (ждём
  `confirmation_url`), `invoice-request` (`{"ok":true}`). Негативные кейсы (без email → 400, не 500).
- **6.2. Сквозной прогон в браузере** (оплата → страница ЮKassa с верным продавцом/суммой;
  счёт → сделка в нужной воронке с компанией и контактом).
- **6.3. Логи с контекстом** (`account_id`, суммы, id сущностей). Best-effort обогащение не роняет запрос.
- **6.4. Понятные тексты ошибок API** (реальная причина, а не «задайте переменную», которая уже задана).

## Чек-лист перед запуском биллинга

- [ ] `docker-compose`: `env_file: .env` + критичные переменные в `environment`; всё новое — в `.env.example`.
- [ ] Валидация env на старте (fail-fast), пустые строки → default.
- [ ] Секреты только в `.env`, плейсхолдеры в `.env.example`, ничего в git.
- [ ] ЮKassa: `receipt` (54-ФЗ) с `vat_code`, поле email/телефон в форме, валидация.
- [ ] Вебхук ЮKassa: перепроверка по id, ответ 200, (опц.) IP-allowlist.
- [ ] Вендор-CRM: внешняя интеграция + долгосрочный токен в `.env`.
- [ ] Кастом-поля: сверены `field_id` и сущность (lead/contact/company) через API.
- [ ] Сделка-счёт: компания (account_id) + контакт (телефон/email) линкуются к сделке.
- [ ] Дедуп компаний/контактов/сделок; хранение `vendor_*_id`.
- [ ] Этапы воронки — явными ID в `.env`.
- [ ] Сделка при установке + бэкфилл + идемпотентность/оживление.
- [ ] Виджет: локации ↔ функции, `code`/`secret_key`, `pass` для секретов, `required` где нужно,
      escapeHtml, i18n-паритет, semver, zip с manifest в корне.
- [ ] Виджет показывает реальные ошибки, не заглушки.
- [ ] Smoke-тесты (`health`/`checkout`/`invoice`) + сквозной прогон + тестовый магазин ЮKassa.
